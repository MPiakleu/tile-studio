# Tile Studio v1.4.4 — Root-cause review and acceptance plan

## Root causes (verified from v1.4.3 source)

### P0: settings editor disappears after inactivity

`TileStudioWebPart.ts::onPropertyPaneConfigurationComplete()` unconditionally unmounted the custom pane and cleared `PropertyPaneSession`. **SharePoint can invoke this method after a completion timeout while the pane is still open.** The previous implementation consequently erased the controls until the pane was reopened. The correct lifecycle ownership is: keep the editor mounted while `context.propertyPane.isPropertyPaneOpen(instanceId)` is true; unmount only on actual close or the custom field's `onDispose`. This avoids replaying a stale host callback and preserves unsaved draft/UI state.

**Regression test:** `tests/property-pane-lifecycle.test.cjs` simulates an open pane, edit, three idle completion callbacks, further edits, then a genuine close. It asserts no premature unmount or loss of callback, tab, or final property bag.

Reference: SPFx documented property-pane lifecycle and public `IPropertyPaneAccessor.isPropertyPaneOpen()` API.

### P1: layout switching barely changes visual appearance

`TileCollection.tsx` can render a tile as either `TileCard` (legacy) or `ComposedTile` (advanced). Much of `TileCollection.module.scss` previously styled only `.cardInner`, `.copy`, `.iconSlot`, `.footer`. `ComposedTile` instead outputs `.composeBody`, `.composeCopy`, `.composeIcon`, `.composeFooter`. Most of the listed layouts therefore shared the same composed appearance. Additionally, `LayoutSection.tsx` only changed the `layout` ID and (conditionally) minimum height, while `preview/Preview.tsx` applied many additional layout-specific settings. The actual designer thus could not match the showcased examples.

**Fix:** all ten layout IDs have explicit composed layout styles; a single `models/layoutProfiles.ts` supplies structural defaults to both the SharePoint editor and preview gallery. Profiles intentionally change columns/height/spacing/alignments on **layout selection**; the user's tile content, source, color choices, link behavior and composition overrides remain intact. The old configuration schema and solution ID remain unchanged.

**Regression tests:** `tests/layout-contract.test.cjs`, `tests/settings-matrix.test.cjs`, new actual-button computed-style checks in `tests/browser.cjs`.

### Additional resilience — recoverable editor errors

`StudioEditor.tsx` previously had no React error boundary of its own (only the web part preview was protected). A future unexpected render exception could erase the custom settings controls with no useful message. An editor-specific error boundary now displays an accessible explanation and a **Retry settings** button. This is a last-resort recovery state; it does not replace fixing or diagnosing an exception.

## Mandatory test tenant acceptance

1. Back up the existing `.sppkg`, export the web-part configuration, and preserve the page version. Upgrade the *same* app catalog solution to 1.4.4.0 in a staging site after `npm ci && npm run package` succeeds.
2. Open the SharePoint web-part properties pane. Make a setting change. **Leave it open for 10–15 seconds without interacting**; confirm all setting tabs still exist. Change another value and confirm the live preview updates. Repeat five times, including after switching between tabs. This directly tests the reported failure.
3. Under **Layout**, switch among **Action Cards, Compact Tiles, Resource List, Icon Grid, Minimal Links**. Confirm the changes are visibly different and do not remove manual tiles, links or SharePoint data-source configuration. Check both classic and nonclassic composition templates.
4. Use **Done editing**, then SharePoint **Save as draft / Publish**, hard reload, reopen properties and verify the last setting and selected layout persist.
5. Switch repeatedly between web parts and reopen the pane; confirm **Visibility** does not accumulate, and custom controls do not disappear or lose focus. Test use of two Tile Studio instances on the same page.
6. Test 320, 375, 390, 600, 768, 1024 and 1440px container widths, plus short windows, using a mix of missing data and long text. Confirm actions do not overlap, no horizontal scrolling, keyboard focus remains visible, and reduced-motion is respected.
7. Test manual/SharePoint modes, a 403 list-access failure, import/undo, color overrides, and a zero-tile state. Review actual tenant console logs if anything still collapses.

## Build on a development workstation

```powershell
npm ci
npm run package
npm run test:browser  # browser dependencies and Playwright Chromium required
```

Only a successful native build can generate `sharepoint/solution/imberon-tile-studio.sppkg`. **Do not deploy this source ZIP directly as a package.**

## Rollback

Retain the previous `.sppkg` and the SharePoint page version. If the staging acceptance fails, redeploy the last verified package and restore the page version if necessary. There is no schema or API-permission migration to reverse.
