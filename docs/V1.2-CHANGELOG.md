# Tile Studio v1.2.0 — Phase 1 followed by Phase 2

## Phase 1 — Card composition and actions

Seven compositions share a bounded `CompositionSettings` model: `classic`, `help`, `service`, `buttons`, `health`, `news`, and `resource`. Each has editable header mode, category and eyebrow flags, optional badge/status regions, and three independent footer slots. Layouts do not impose a rigid internal card hierarchy. A custom renderer handles independently clickable primary and secondary actions without nested anchors.

The native right-hand property pane provides all controls. Classic rendering continues to use the original component when configuration has not opted into a new composition, preserving the original tile interaction. Existing layout IDs and solution IDs are unchanged.

Added separate action links and button variants; approval/metadata badges; status info pill; category icons; optional category uppercase style; footer anchoring; configurable padding, min-height, font-size and line-height; responsive stacking; user-reduced-motion support.

## Phase 2 — Fine tuning, shared presets and connected content

A tile's `appearance` structure contains allowlisted and validated per-tile values; it can select its own composition template, override chosen footer slots and certain style parameters. Unspecified values inherit section settings. Use **Reset overrides** for an individual tile.

An optional `sharedPresetSource` refers to an authorized same-tenant SharePoint list. It reads up to 50 entries containing the `PresetJson` field as JSON with `design` and `responsive` objects. Bad JSON is ignored; auth errors surface to editors. The component never writes to that list.

Connected list mapping adds `buttonLabel`, `secondaryLabel`, `secondaryUrl`, `categoryIcon`, `visibilityCondition`, and `compositionTemplate`. Sorting, limits, field-identifier validation and read-only request context remain unchanged.

A bounded, explicit `visibilityCondition` filters tile presentation; it grants no authorization and must not be used to hide sensitive information.

Schema v2 reads schema v1 and v2 and normalizes historic settings with default composition values. The SPFx custom property-pane lifetime controls from v1.1.1 remain intact. Partial URL input is retained transiently in the editor while only safe normalized values enter the persisted property bag.
