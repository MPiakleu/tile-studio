# Tile Studio v1.2.4 — Repeated SharePoint Visibility Control Fix

## Confirmed failure mode

In v1.2.3, **every design edit** still invoked the SharePoint custom-field `changeCallback('config', ...)`. SharePoint uses that callback to process a property change and may reconstruct its property pane (including the framework-owned `Visibility — Show in mobile and email view` group). Returning fresh configuration arrays (v1.2.3's approach) was insufficient in the production SharePoint runtime, as reported after upgrade. The cause of Microsoft's internal duplication remains an inference; this package stops the associated repeated reconfiguration on the Tile Studio side and requests framework-level suppression of the group.

## Changes

1. **Prevent a full framework change for every interaction.** Only the first edit of a property-pane session calls the framework change callback (or protected fallback). Subsequent edits update `this.properties.config` and the React preview directly, retaining the latest value for serialization. This reduces repeated pane rebuilds and potential editing freezes. The notification gate resets after the pane closes, page edit mode ends, or properties are deserialized.
2. **Do not render native Visibility controls for this web part.** Add `disableVisibilityGroup: true` to `getPropertyPaneConfiguration()`. This is the *documented* SPFx configuration property for excluding that automatically injected group. Microsoft currently labels it a **preview API**, so it could change in a future SharePoint update. Tile Studio's own per-tile and responsive visibility controls are unchanged.
3. **Preserve property-pane reliability fixes:** Stable custom-field identity, disposal-order safeguards, React cleanup, draft state, cursor/focus recovery and pending edits across host remounts remain intact.
4. **No DOM surgery:** No code searches for or removes SharePoint-rendered elements, so the fix cannot accidentally remove unrelated sections or other web parts' controls.

## Behavior change

SharePoint's **Show in mobile and email view** toggle will be **absent** from the Tile Studio property pane when the SPFx host honors `disableVisibilityGroup`. Previously saved web-part visibility configuration is not modified by this patch. An administrator needing to change that SharePoint-owned feature should do so before upgrading, or use a separate SharePoint-native method. This does not affect Tile Studio's tile visibility, responsive layout, mobile columns, or per-tile hide rules.

## Safety and persistence tradeoff

A custom property pane typically calls the framework `changeCallback` on every change. Tile Studio now notifies it **once per editing session**, while changing the web part's authoritative property bag on all subsequent edits. This preserves live preview and is intended to preserve saved changes through `onBeforeSerialize`, but **must be verified in actual SharePoint**. Specifically, publish and reload after multiple subsequent edits in the same session; the final edit (not merely the first) must persist. If not, do not deploy broadly—use the previous version until a supported transaction/Apply flow is implemented.

## Validated locally

- Automated TS/TSX parsing and 89 Node unit/regression tests, including 100 consecutive edits, 50-value serialization, pane remount, repeated configuration-start, and fresh editing sessions.
- Normalized design/config modules compile with globally installed TypeScript.
- Production `npm ci`, Heft lint/webpack, SharePoint client-side integration and real property-pane behavior are **not** verified here (npm registry resolution failed).

## Required SharePoint acceptance checks

1. Build `1.2.4` from a clean extract, deploy **to a draft/test page first**, and perform a hard reload before opening the editor. Older loaded v1.2.3 scripts can remain cached until reload.
2. Open Tile Studio property pane; native `Visibility — Show in mobile and email view` should no longer appear. If it appears, record SharePoint host version and stop rather than hiding it with DOM code.
3. In a single pane session, perform 30+ edits: titles, card backgrounds, accent, slider adjustments, template/preset changes, responsive columns and individual tile overrides. Confirm there are **zero repeated** Visibility groups and that the editor never freezes.
4. Make changes **after** the first edit, such as setting one tile background to `#DCFCE7` then title to `Final persisted value`. Save/publish, reload, and confirm the **last** values persist.
5. Close/reopen the pane and repeat, verifying no accumulation, and verify an older existing Tile Studio instance keeps its original design.
6. Check the regular and mobile view; original global/tile visibility and permission-trimming behavior are intact.

## If the native group still appears

Do not manipulate SharePoint DOM. The SPFx flag is Microsoft-preview, and behavior can vary with tenant rollout. At that point, move Tile Studio to a fully supported non-reactive property editing transaction or raise an issue with Microsoft using a minimal property pane reproduction. The automated tests **do not establish** that Microsoft's production pane honored the flag.
